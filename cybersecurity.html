01 · Overview

A Static Portfolio with Hosted Services

The website’s pages and browser scripts are served by Vercel. Supabase can provide account authentication and database services, while a Vercel API route can keep the OpenAI API key off the client.

These services have different responsibilities: a successful sign-in does not automatically protect every static page. Sensitive data and operations still need server-side checks or database policies.

02 · Threat Modeling

STRIDE Threat Assessment

Key risks for a public website with client-side code and hosted authentication, database, and AI services.

Spoofing

Account impersonation

Supabase Auth verifies credentials, but sessions and account recovery still need careful handling. Admin actions must verify authorization independently.

Tampering

Client or request manipulation

Visitors can modify browser code and requests. Validate inputs and enforce permissions in API routes and database policies, not only in the interface.

Repudiation

Limited audit trail

Browser-only logs can be changed or erased by the visitor. They are not reliable audit records; production auditing needs trusted server-side logging.

Information Disclosure

Public source and secrets

Static source may be publicly inspectable. Never expose OpenAI or Supabase secret/service-role keys in browser code. Restrict database access with RLS.

Denial of Service

Availability and cost

Hosting or database outages can interrupt the site. An exposed AI endpoint may also incur usage costs; add rate limits and usage monitoring before broad public use.

Elevation of Privilege

Direct page access

Static pages can be opened directly by URL. Hiding a link does not protect data; enforce authorization for every sensitive API or database operation.

03 · Architecture

Security Responsibilities by Layer

These controls depend on the corresponding services and policies being configured in the deployed project.

Browser

The Supabase publishable key may be used by the browser. It is not a secret; database access must be constrained by RLS. Render user and AI content as text where possible.

Vercel

Vercel serves the site over HTTPS and can run API functions. Keep the OpenAI API key in server-side environment variables; static hosting alone does not restrict page URLs.

Supabase

Supabase Auth manages account sign-in. Database tables should have RLS enabled and policies that limit each user to their own records. Admin roles must not be self-assigned by browser code.

OpenAI integration

The browser should call a server-side Vercel endpoint. That endpoint keeps the OpenAI key private and should validate requests and use rate limits or usage controls.

The browser interface may show or hide controls based on a signed-in session, but that is not a substitute for server-side authorization or Supabase Row Level Security.
04 · Limitations

What This Portfolio Does Not Guarantee

  • A static page is not private just because a navigation link is hidden.
  • Browser storage and browser-side role checks are controlled by the visitor and must not be trusted for access decisions.
  • A Supabase publishable key is expected to be public; RLS and correct policies are essential to protecting database records.
  • An AI endpoint can be abused or generate costs unless it has suitable request limits and monitoring.
  • Client-side messages and local browser logs are not authoritative security audit records.

Recommended Next Steps

  1. Verify RLS is enabled on every user-data table.
  2. Test that one user cannot read another user’s profile.
  3. Keep all secret keys in server-side configuration.
  4. Add rate limiting to the public AI endpoint.
  5. Review deployment logs and service usage regularly.
05 · User Input Security

Handling User Input Safely

Login details, profile names, chatbot messages, and persona descriptions are all untrusted input. Validate them, display them safely, and enforce access rules where data is stored or processed.

Input Validation

Vulnerable: trust browser checks alone
<input maxlength="50" required>

Browser checks help with usability, but visitors can bypass them or send requests directly to an API.

Safer: validate again on the server
function validMessage(value) {
              return typeof value === "string" &&
                value.trim().length > 0 &&
                value.length <= 2000;
            }
            
            if (!validMessage(req.body?.message)) {
              return res.status(400).json({ error: "Invalid message." });
            }

Define allowed types, formats, and maximum lengths for each field. Client-side validation is useful, but server-side validation is essential.

Parameterized Queries & Prepared Statements

Vulnerable: concatenate input into SQL
const sql =
              "SELECT * FROM users WHERE email = '" + email + "'";
            
            const result = await db.query(sql);

SQL syntax entered as part of the value may change the query.

Safer: pass values separately
const result = await db.query(
              "SELECT id, email FROM users WHERE email = $1",
              [email]
            );

Parameterized queries treat input as data. A prepared statement uses a separately defined query and supplied values; database drivers often support both together. Don’t interpolate user values into SQL.

Secure Database Access

Vulnerable: trust a browser-supplied user ID
// A visitor could change req.body.userId.
            const result = await db.query(
              "SELECT * FROM profiles WHERE id = $1",
              [req.body.userId]
            );

This query is parameterized, but it does not establish that the requester owns the requested profile.

Safer: use verified identity and authorization
const user = await getAuthenticatedUser(req);
            
            if (!user) {
              return res.status(401).json({ error: "Sign in required." });
            }
            
            const result = await db.query(
              "SELECT display_name FROM profiles WHERE id = $1",
              [user.id]
            );

Derive identity from a verified session, restrict access with database permissions, and use Supabase Row Level Security (RLS) so users can access only permitted rows.

Display Text Safely

Avoid interpreting user-provided text as HTML. For plain-text messages, use textContent, not innerHTML. 

messageElement.textContent = userMessage;

Limit Abuse

Add rate limits and usage monitoring to public API routes, especially AI endpoints. Keep OpenAI and Supabase secret/service-role keys on the server, never in browser code.

Validation checks whether input is acceptable; parameterized queries and prepared statements help prevent SQL injection; authorization and RLS determine who may access data. These controls solve different problems and should be used together where applicable.

07 · CIC-IDS2018 Network Traffic Study

Detecting DoS/DDoS Traffic with Flow Features

This study explores whether network-flow measurements can help distinguish normal traffic from DoS and DDoS attack traffic.

Dataset

CSE-CIC-IDS2018 Network Intrusion Detection Dataset

Kaggle copy: csecicids2018, published by dhoogla.

View dataset on Kaggle Open Colab Notebook
Dataset description

This dataset contains labelled network-traffic flows collected for intrusion-detection research. The Parquet files include CICFlowMeter flow features—such as packet counts, packet lengths, flow timing, byte rates, and protocol information—and labels for benign traffic and several attack types. The files used in this notebook include DDoS, DoS, brute-force, botnet, web, and infiltration traffic. This project focuses on comparing benign flows with DoS/DDoS flows.

The analysis used a 64,000-row sample drawn from the Parquet files, not every row in the dataset.

Research Question

How effectively can flow-level network features distinguish normal traffic from DoS/DDoS traffic, and how do supervised classification and anomaly detection compare?

The notebook compared feature medians, trained a Random Forest classifier, and tested an Isolation Forest anomaly detector. The Random Forest performed very well on a random split of the sampled flows; the Isolation Forest detected few attack flows. These results are preliminary and do not establish performance on unseen networks or attack conditions.

Findings from the notebook

Normal traffic

In the sample, normal flows had median values of 5 total forward packets, 343 forward packet bytes, and 50 for mean forward packet length. These are dataset observations, not universal definitions of benign traffic.

DoS/DDoS traffic

Combined attack flows differed from normal flows in several features. For example, median forward packet bytes and mean forward packet length were 0 in the attack sample. Median minimum forward inter-arrival time was 20,957.5, compared with 34 for normal flows. These patterns are candidates for investigation, not universal attack signatures.

Traffic volume and patterns

Packet counts, byte totals, packet lengths, flow rates, timing, and TCP flags can help characterize traffic. The notebook found different medians for several of these features. Its initial traffic-volume plots were not produced because the expected column names did not match the dataset’s column names.

Abnormal behavior

Statistical summaries can help identify differences from a normal baseline, while anomaly detection can flag unusual flows. An unusual flow is not automatically malicious; the Isolation Forest results show that anomaly detection did not reliably identify DoS/DDoS traffic in this experiment.

Supervised · Random Forest

Classification result

On the notebook’s random train/test split, the model classified about 99.66% of the 16,000 test rows correctly. 

             Predicted
                                     Normal  DoS/DDoS
            Actual Normal            11959       41
                   DoS/DDoS              14     3986

This is a random-split result from a capped sample, not an independent test on a separate capture or time period.

Anomaly detection · Isolation Forest

Anomaly-detection result

The tested Isolation Forest identified only 60 of 4,000 attack flows in the test set. 

             Predicted
                                     Normal  DoS/DDoS
            Actual Normal            10997     1003
                   DoS/DDoS            3940       60

In this experiment, being unusual did not reliably mean that a flow was a DoS/DDoS attack.

Most important Random Forest features

The model’s highest-ranked features included Subflow Fwd Bytes, Fwd Packets Length Total, Fwd Packet Length Max, and Init Fwd Win Bytes. Feature importance shows how the model used the sample; it does not establish a universal attack signature.

Limitations: The notebook capped the sample at 5,000 rows per file and category and used a random train/test split. Similar flows from the same source files could appear in both sets, making the Random Forest result optimistic. The expected traffic-volume feature lookup also used names that did not match the available columns, so the intended volume plots were skipped. A stronger evaluation should correct the feature-name mapping and test on separate files or time periods.
Conclusion: Statistical comparisons and supervised machine learning revealed differences between the sampled normal and attack flows. The Random Forest performed strongly on the random split, while the tested Isolation Forest missed most attacks. Further evaluation is needed before drawing conclusions about real-world detection performance.
